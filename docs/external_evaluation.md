# External images and pose-detector comparisons

Existing annotation-trained pose checkpoints can classify detected poses without
retraining. Both detectors return up to two COCO-17 skeletons in original pixel
coordinates, then the classifier receives the same 102 values produced by
`pose_features` during training: pair-normalized x/y and joint confidence.
Missing athletes/joints are zero-filled. No inference-time augmentation is used.

The two evaluation tasks answer different questions:

- **External evaluation:** how well do saved classifiers generalize to the new
  labeled images? Supports the three pose classifiers, ResNet-18 and DINOv3.
- **Original-data pose comparison:** how much does replacing supplied skeletons
  with YOLO or ViTPose affect a fixed pose classifier on the same validation/test
  frames? This verifies the exact annotations and split saved by the checkpoint.

## Install optional detector dependencies

From the DGX project directory, after the normal bootstrap:

```bash
.venv/bin/python -m pip install -r install/requirements-pose-detectors.txt
```

The first uncached extraction downloads YOLO26x-pose and/or RT-DETR R50 plus
ViTPose++ Huge. Hugging Face models use the normal `HF_HOME` cache; YOLO weights
are stored in `Data/pose_detectors/`. Image-only evaluation and supplied-pose
evaluation do not need these detector packages or downloads.

YOLO26 requires Ultralytics 8.4 or later. After switching from YOLO11, use a
new `--cache-dir` (for example, `diagnostics/pose_detectors/yolo26_cache`).
Detector metadata records the model name and weights hash; old YOLO11 caches
are rejected rather than reused as YOLO26 results. Existing reports and caches
can be kept for comparison.

Commands below use existing trusted project checkpoints. Replace `RUN_NAME`
with a directory under `trainings`; repeat `--checkpoint` to compare more runs.
Passing a run directory selects `checkpoints/best.pt`; pass `last.pt` explicitly
to evaluate that checkpoint instead. `--device cuda:0` selects GPU 0 visible to
the process; CPU and MPS are also supported. Models are loaded sequentially.

## Evaluate the new image set

```bash
bash launchers/EVALUATE_EXTERNAL.sh \
  --checkpoint trainings/RUN_NAME/checkpoints/best.pt \
  --pose-source all --device cuda:0
```

The launcher defaults to the included images and annotations under `Data/`.
For an image checkpoint, inference uses RGB, the same 224-pixel letterbox and
ImageNet normalization as training. For a pose checkpoint, `--pose-source all`
compares the saved skeletons with fresh YOLO and ViTPose detections. Use
`--pose-source annotations` for saved skeletons only, or `yolo`/`vitpose` for
one detector plus the reference baseline. Image checkpoints use image input
regardless of this pose option.

With detector input, every labeled external image is evaluated, even if it has
no saved reference poses. Only the supplied-pose baseline and paired comparisons
require two usable reference skeletons. The report gives both population counts.

```bash
bash launchers/EVALUATE_EXTERNAL.sh \
  --checkpoint trainings/MLP_RUN \
  --checkpoint trainings/WIDE_RUN \
  --checkpoint trainings/ATTENTION_RUN \
  --checkpoint trainings/RESNET_RUN \
  --checkpoint trainings/DINOV3_RUN \
  --pose-source all --device cuda:0
```

There are **99 unique images** across 10 classes: 9 half-guard images and 10 of
each other class. One exact half-guard duplicate was removed without renumbering
the remaining images. The position labels are human annotations. The saved
skeletons were generated by ViTPose++ Huge with RT-DETR; they are **not manually
verified keypoint ground truth**. Comparing fresh ViTPose to these skeletons
measures agreement with the saved extraction, not independent pose accuracy.
The metadata sidecar records these limitations. Original source URLs and
independence from the training collection were not recorded/verified.

The external loader accepts relative image paths including their extensions,
checks image SHA-256 values when supplied, and rejects duplicate file contents,
unsafe paths and malformed annotations. It intentionally evaluates different
data from training, while retaining training hashes and checkpoint identity in
the report. This does not relax the original evaluator's split checks.

## Compare supplied versus detected poses on original frames

Start with a small validation pilot:

```bash
.venv/bin/python experiments/compare_pose_detectors.py \
  --checkpoint trainings/POSE_RUN \
  --detector all --split val --limit 20 --device cuda:0
```

Use all eligible validation frames and all three pose checkpoints:

```bash
.venv/bin/python experiments/compare_pose_detectors.py \
  --checkpoint trainings/MLP_RUN \
  --checkpoint trainings/WIDE_RUN \
  --checkpoint trainings/ATTENTION_RUN \
  --detector all --split val --all-frames --device cuda:0
```

The default split file is the exact file recorded in each checkpoint, including
`multiview_sections_shifted.json` when that was used for training. If paths have
moved, the tool searches local split files for the saved SHA-256, or accepts
`--split-file Data/splits/multiview_sections_shifted.json`. A different split is
rejected before model/detector inference. `--split test` selects final test data.
Without `--all-frames`, the default is a reproducible sample of up to 150 frames
per class. `--holdout` selects the complement of that sample in the same partition;
it does not create a new training split.

Each comparison reports:

- Reference-pose baseline and detector-input classification on exactly the same
  selected frames, including zero/one-athlete detection failures.
- Coverage and a paired comparison restricted to frames where a detector finds
  two usable skeletons; also the common two-athlete subset across all detectors.
- Accuracy, macro F1, per-class precision/recall/F1/support and confusion matrices.
- Per-image predicted classes and probabilities, so incorrect predictions can be
  inspected individually. Original multiview splits also report held-out-view
  and unseen-moment results separately.
- Joint-position agreement with the reference after choosing the better of the
  two possible athlete assignments. This normalizes distances by the reference
  pair's bounding-box scale; it is not a standalone pose-estimation benchmark.

YOLO retains its two highest-confidence person detections and masks entire joints
below confidence 0.5. ViTPose uses RT-DETR's person detections, removes near-identical
boxes, and estimates up to two skeletons. Neither detector knows which people
are the competing athletes when referees or spectators are visible. Classifier
input preserves detector order; localization scoring alone chooses the best
assignment. The classifiers' existing athlete-swap augmentation is unchanged.

## Detection caches and optional retraining

For both detectors on every annotated image, use the
[full-dataset extraction queue](pose_extraction_queue.md). It distributes chunks
as GPUs become available and merges verified caches for training.

Detection files contain image IDs, image SHA-256, raw poses and elapsed time;
sidecars record detector settings, package versions and weight identity. Output
directories are created automatically. Rerunning resumes an interrupted
extraction and reuses detections across classifiers. A changed image or detector
configuration is rejected. Legacy unverified caches must be regenerated in a new
`--cache-dir`; keep one writer per cache directory.

The original-data comparison uses `diagnostics/pose_detectors/verified_cache`.
To prepare a training cache deliberately, specify the exact training manifest:

```bash
.venv/bin/python experiments/extract_poses.py \
  --split-file Data/splits/multiview_sections_shifted.json \
  --split train --detector vitpose --device cuda:0
```

That cache can be supplied to training through `--pose-detections`; it is optional
and is **not required** to evaluate existing annotation-trained models. Training
resume verifies the cache checksum and rejects modifications rather than silently
changing training data. Finish extraction before starting a run that consumes the
cache; adding rows afterward changes the checksum too.

The detector integrations follow the
[Transformers ViTPose API](https://huggingface.co/docs/transformers/v4.57.1/en/model_doc/vitpose)
and [Ultralytics prediction API](https://docs.ultralytics.com/modes/predict/).
